# Go-бэкенд: orchestrator

Сервис запускает HTTP `GET /healthz` и `POST /analysis?job_id=<UUID>`,
подключается к PostgreSQL, применяет SQL-миграции через Goose и подготавливает
демонстрационный регион СПб в MinIO и PostgreSQL. Создание задачи сохраняет
`jobs` и команду `START` в `outbox` одной транзакцией. Фоновый отправитель
публикует команды в Kafka `analysis.commands` и отмечает их как `READY`.
Получение результатов из `analysis.results`, heartbeat и отмена через HTTP пока не подключены.

## Что установить

- Для запуска в Docker: Docker Desktop с Linux containers и Compose v2.
- Для команд Makefile: GNU Make. На Windows нужен Git for Windows с `sh` в `PATH`.
- Для запуска Go на компьютере: Go 1.27.1.

Все команды ниже выполняются из корня репозитория.

## Запуск в Docker

При первом запуске создай `.env`, если его ещё нет:

```powershell
# Windows / PowerShell
Copy-Item .env.example .env
```

```sh
# Linux / Git Bash
cp .env.example .env
```

В `.env` заполни `GO_DB_NAME`, `GO_DB_USER`, `GO_DB_PASSWORD`,
`S3_ACCESS_KEY` и `S3_SECRET_KEY`. Пример содержит имена базы и пользователя
`orchestrator`; пароли замени своими. `.env` не коммитится.

```sh
make build
docker compose ps
docker compose logs -f orchestrator
```

`make build` собирает образы и запускает четыре сервиса. MinIO собирается из
исходников, поэтому первая сборка может занять несколько минут.
`make run` запускает окружение без принудительной пересборки.

Без Make та же команда запуска:

```sh
docker compose up -d --build
```

| Сервис | Адрес с компьютера | Адрес внутри Docker |
| --- | --- | --- |
| Go HTTP | `http://localhost:8080/healthz` | `orchestrator:8080` |
| PostgreSQL | `localhost:5432` | `postgres:5432` |
| Kafka | `localhost:9092` | `kafka:19092` |
| MinIO API | `localhost:9000` | `minio:9000` |
| MinIO Console | `http://localhost:9001` | `minio:9001` |

В MinIO Console используй `S3_ACCESS_KEY` как логин, `S3_SECRET_KEY` как пароль.

## Демонстрационный регион СПб

Исходный GeoJSON лежит в `testdata/spb.geojson`: одна Feature с геометрией
MultiPolygon. Файл сохранён без преобразования координат и свойств.

При старте Go-приложение создаёт бакет `regions`, если его ещё нет,
и загружает `testdata/spb.geojson` с ключом `spb.geojson`, если объект отсутствует.
Существующий объект не перезаписывается. Затем приложение создаёт или находит
запись региона в PostgreSQL и выводит её `region_id` в логе `demo region ready`.
Этот UUID используй в теле запроса `POST /analysis`.

Локально запускай приложение из каталога Go-сервиса, например через
корневой `make run-local`: путь к файлу считается относительно рабочего каталога.
В Docker демонстрационный GeoJSON включён в образ.

## Конфигурация

`config/config.go` читает YAML по `CONFIG_PATH` и переменные окружения.
Без `CONFIG_PATH` используется только окружение. Переменные имеют приоритет над YAML.

`CONFIG_PATH` выбирает источник настроек, а не способ запуска:

- Весь backend в Docker: `make build`. Путь к YAML указывать не нужно.
- Go на компьютере с YAML: укажи `CONFIG_PATH=config/config.yaml` в корневом `.env`.
- Go на компьютере без YAML: оставь `CONFIG_PATH=` пустым в `.env`.

Для Go на компьютере PostgreSQL, Kafka и MinIO должны быть доступны отдельно.
Перед запуском заполни в `.env` `DSN`, `S3_ACCESS_KEY` и `S3_SECRET_KEY`:
в примере YAML эти обязательные значения пустые. Используй локальные адреса сервисов.

Для YAML укажи в `.env`:

```dotenv
CONFIG_PATH=config/config.yaml
```

Затем из корня проекта:

```sh
make run-local
```

Путь здесь считается от `backend/orchestrator-service`, куда переходит Make.
Makefile сервиса читает корневой `.env` и передаёт его переменные Go-процессу.
Используй формат `KEY=value` без кавычек, как в `.env.example`.
При прямом запуске `go run ./cmd/app` без Make переменные задаются в терминале или IDE.

В Docker настройки читаются только из окружения, YAML не подключается.
В секции `orchestrator.environment` файла `compose.yaml` заданы
`APP_NAME`, `LOG_LEVEL`, `HTTP_ADDRESS`, `HTTP_TIMEOUT`, `SHUTDOWN_TIMEOUT`,
`DSN`, `S3_ENDPOINT`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `KAFKA_ADDRESS`.
Их имена совпадают с `env`-тегами Go-конфига.

Compose сам читает корневой `.env` и передаёт выбранные значения контейнерам.
При `make run-local` это делает Make. Go-приложение самостоятельно `.env` не загружает;
godotenv в код приложения не добавляется.

## Миграции и хранение данных

При старте `runApp` после подключения к PostgreSQL вызывает `RunMigrations` из `main.go`.
Функция открывает подключение через `sql.Open("pgx", dsn)` и вызывает
`goose.Up(db, "migrations")`. SQL читается из папки `migrations` относительно
рабочего каталога: локально запускай через Make, в Docker папка уже копируется в образ.
Goose 3.26.0 применяет ещё не выполненные миграции по номеру и сохраняет версии
в таблице `goose_db_version`. При ошибке миграции HTTP-сервер не запускается.
Используется тот же `DSN`; подключение миграций закрывается после их выполнения.

Для ручного управления есть CLI Goose:

Команды `make migrate-status`, `make migrate-up`, `make migrate-down` читают
`GOOSE_DRIVER=postgres` и `GOOSE_DBSTRING=${DSN}` из корневого `.env`.
Файл загружает сам CLI Goose через `-env ../../.env`; Go-приложение по-прежнему
не загружает `.env` самостоятельно.

Начальная схема содержит `regions`, `jobs`, `graphs`, `metrics`, `outbox`, `inbox`.
В `regions` хранится ключ GeoJSON в MinIO; в `jobs` — регион, транспорт, статус
и координаты двух углов. Граф и массив метрик пока хранятся целиком в JSONB,
по одной записи каждого вида на задачу. Формат соответствует `backend/api/openapi.yaml`.
Go-обработчик проверяет виды транспорта, сортирует их и убирает повторы;
SQL ограничивает количество элементов и допустимые значения.

Порядок работы с сообщениями:

- Изменение задачи и вставка команды в `outbox` — одна транзакция PostgreSQL.
  Для запуска и отмены создаются разные строки с `command_type = START / CANCEL`.
  `payload` содержит снимок параметров команды. В Kafka для запуска передаются
  две точки области и виды транспорта; GeoJSON, регион и ключ MinIO не передаются.
  Для отмены достаточно пустого объекта.
  `job_id` и тип команды отправляются вместе с payload, а `outbox.id` служит ID сообщения
  и не меняется при повторной отправке. Текущий статус из `jobs` при отправке не подставляется.
- После подтверждения Kafka отправитель меняет `PENDING` на `READY` по `outbox.id`.
  Для порядка команд нужен один последовательный отправитель на задачу:
  сначала подтверждается запуск, затем отправляется отмена. В одном топике
  используется Kafka key = `job_id`. Сама таблица порядок отправки не обеспечивает.
- Для входящих результатов `inbox.id` берётся из сообщения. Вставка inbox,
  сохранение результата/статуса задачи и установка `READY` — одна транзакция.
  При конфликте по уже обработанному id повтор не применяет бизнес-изменения.
  При ошибке транзакция откатывается целиком, сообщение можно обработать повторно.

Отправитель outbox запускается из `main` и распределяет задачи по пяти каналам
по хешу `job_id`. Команды занятой задачи остаются в PostgreSQL до завершения
предыдущей отправки. При ошибке Kafka или записи `READY` сообщение повторяется
с прежним ID. Обработчик входящих результатов и inbox пока не реализован.
Время heartbeat и сведения об ошибке задачи также пока не хранятся.
Go-сервис владеет этими шестью таблицами; таблицы Python-воркера эти миграции не меняют.
Потребитель команд в Python должен самостоятельно обрабатывать повторы в своей БД.

Пока миграция нигде не применена, её SQL можно редактировать. После применения
добавляй новый SQL-файл со следующим номером, секциями `-- +goose Up` и
`-- +goose Down`; старые применённые файлы не переписывай. После добавления SQL
пересобери Docker-образ, чтобы новая миграция попала в его папку `/migrations`.
`make migrate-down` откатывает все миграции до версии 0 и удаляет созданные ими таблицы с данными.
При следующем старте приложение снова применит отсутствующую миграцию.

## Логи и остановка

```sh
docker compose logs -f             # все сервисы
docker compose logs -f orchestrator
make stop                         # остановить окружение, сохранив данные
make run                          # запустить снова
```

Локальный Go-процесс останавливается через `Ctrl+C`. В Docker приложение получает
`SIGTERM`, завершает HTTP-запросы и ожидает остановки фоновых воркеров перед
закрытием Kafka producer и пула PostgreSQL.

Logger создаётся в `main` с настроенным `LOG_LEVEL` и передаётся контроллеру,
usecase и отправителю outbox. Поле `component` различает `http`, `analysis` и `outbox`.

Для каждого HTTP-запроса, кроме `/healthz`, middleware пишет метод, путь и длительность.
Паника обработчика записывается в лог со стеком; клиент получает JSON с кодом
`internal_error` и HTTP 500, если ответ ещё не был начат.
Неожиданные ошибки HTTP-операции логируются в контроллере на уровне ERROR;
ошибки валидации и конфликты не записываются как серверные сбои.
Usecase пишет создание задачи на INFO и возврат существующей задачи на DEBUG.
Фоновый отправитель пишет успешную доставку на INFO, отдельные неудачные попытки
на DEBUG, назначение повтора на WARN и ошибки чтения outbox на ERROR.
Адаптеры передают причину ошибки вызывающему коду и не дублируют её в логах.

Kafka key — строковый `job_id`; `kafka.Hash` направляет команды одной задачи
в одну партицию при неизменном количестве партиций. В JSON передаются
`message_id` (из `outbox.id`), `job_id`, `type` и `payload`.
Для `START` payload содержит `area.first_point`, `area.second_point` и `transports`;
для `CANCEL` — пустой объект. Новая команда получает собственный `message_id`,
а повтор сохраняет прежний. Получатель использует `message_id` для Inbox;
Kafka key служит для выбора партиции и не устраняет дубли.
Producer разрешает создание `analysis.commands` при первой отправке,
если автоматическое создание топиков разрешено на Kafka-брокере.

Данные находятся в volumes PostgreSQL, Kafka и MinIO. Если намеренно нужно удалить
все данные этого окружения, для этого есть отдельная команда `make stop-volumes`.
Изменение пароля PostgreSQL в `.env` не меняет пароль в уже созданной базе.
